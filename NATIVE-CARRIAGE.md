# PORTER Native Carriage/1

Native carriage treats Porters as the network participants and Hosts as absent
from the network. A Host addresses a service identity such as `harmonicdb`; its
local Porter owns the current rendezvous used to approach the Porter responsible
for that identity.

```text
identity      harmonicdb
rendezvous    { lower transport location, current port, Porter public key }
route         direct in this two-Porter experiment
transport     framed TCP byte movement
```

Identity is correspondence meaning. Rendezvous is replaceable carriage
knowledge. Route is trivial and direct in 1.4. TCP is an implementation
mechanism hidden below the protocol. Neither a hostname, port nor connection is
visible to Host code or persisted in LG, Package, IN, SC, CG, CM, AC or CL.

The experiment remains one-Porter-per-service. A Porter has a stable
cryptographic identity associated with that represented service boundary; it
does not yet establish multi-tenancy or transferable service representation.

## Native Unit

A frame contains a fixed nine-byte header:

```text
magic "PRTR" | version 1 | unsigned 32-bit protected-envelope length
```

The bounded protected envelope names native protocol version, stable Unit
identity, Unit class, sending Porter identity and intended recipient identity.
Its payload is canonical JSON encrypted with AES-256-GCM. The key is derived by
HKDF-SHA256 from authenticated X25519 Porter keys and envelope metadata. These
are standard `cryptography` primitives, not bespoke cryptography.

Sender, recipient, Unit identity and Unit class are authenticated additional
data. Captured carriage cannot be redirected, reclassified or attributed to a
different Porter. A 512 KiB ceiling is checked before body allocation. At most
32 incomplete connections are admitted concurrently and each has a two-second
read deadline.

Outer carriage distinguishes `PACKAGE`, `CEREMONY`, `ACCEPTANCE_EVIDENCE`,
`REFUSAL_EVIDENCE` and `CEREMONY_RESULT`. It does not interpret application
payloads. Package admission still creates AC and eventual Host CL; ceremony is
evaluated by the Porter and may create SC but never Host custody.

## Asynchronous evidence

Sending a Unit produces no protocol response. A successful `sendall` says only
that the lower transport accepted bytes. Remote AC evidence and ceremony results
are separate protected Units travelling in the opposite direction.

The origin retains its Package/CM Unit until durable evidence arrives. The
recipient may create AC and lose the return path; origin knowledge remains
`ACCEPTANCE_UNKNOWN`. Repeating the exact Unit reproduces the same AC evidence.
Evidence Units can be regenerated by Package/CM replay, avoiding an infinite
acknowledgement-of-acknowledgement chain.

Recipient absence leaves the durable outgoing Unit intact. Retry policy is
currently a fixed 200 ms laboratory cadence. Connections are disposable and
carry no correspondence truth; one Unit per connection and future connection
reuse are semantically equivalent.

## Explicit limits

The 1.4 rendezvous map is locally configured. Docker DNS supplies a lower-level
location lookup but is not treated as Porter identity. Moving rendezvous still
requires updating/restarting carriage configuration at the origin. Automatic
discovery, authenticated mapping updates, routing beyond one hop, key rotation
and production protection of private-key provisioning remain unimplemented.
